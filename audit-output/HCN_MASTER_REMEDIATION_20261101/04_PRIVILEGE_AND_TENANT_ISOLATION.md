# 04 — Platform Owner separation and tenant isolation

## D1 — Platform Owner cannot be created or promoted by any customer-organization path

**Mechanism** (pre-existing, not modified this pass; verified by reading the current migration history, not assumed):

- `profiles.role` is excluded from the `authenticated` database role's writable column set entirely (migration `012_profiles_revoke_client_role_authority.sql`) via column-level `REVOKE`/`GRANT`, independent of row-level RLS. Even though the self-update RLS policy (`"Users can update their own profile"`, `USING (auth.uid() = id)`) would otherwise permit a caller to update their own row, PostgREST (and any other Postgres client) cannot include `role` in that UPDATE at all -- the column grant blocks it regardless of row ownership. This closes the exact SEC-002 finding migration 012's own header documents: "profiles_update permits id=auth.uid() ... Ordinary non-temp user can change their own role at the database authorization layer," including the specific live-code example of the admin panel's `saveUser()` being reachable against the caller's own id.
- The only role-changing path, `admin_set_role(p_user_id, p_role)`, requires the CALLER's own `profiles.role` to already be `admin`/`superadmin` (`RAISE EXCEPTION 'Only admins can change another account''s role'` otherwise) and explicitly rejects `p_user_id = auth.uid()` even for an existing admin (migration `012`, re-confirmed unchanged through migration `022_pending_role_support.sql`'s later revision of the same function).
- No registration, organization-creation, invitation, membership-update, or license-purchase path in this codebase writes `profiles.role` at all -- every one of those flows operates on `organization_memberships.org_role` (a separate, per-organization-scoped column on a separate table), never on the platform-level `profiles.role`.

**Not independently re-executed live this pass** (pre-existing, unrelated to anything changed in Phases A/B of this engagement; the mechanism's own design -- a column grant PostgREST itself enforces, not a row policy -- is not the kind of thing this session's changes could have affected). Flagging as **PASS by code/migration-history verification**, not by fresh execution, per the directive's own instruction to distinguish the two.

## D2 — Organization Owner (multiple organizations) does not imply Platform Owner privilege

`am_i_org_owner()` / the Organization Owner self-assignment mechanism (migration `144_package1_organization_owner_self_assignment.sql`) is explicitly scoped **per organization** -- confirmed by the already-passing `tests/integration/package1OrgOwnerSelfAssignment.test.ts` (5/5 tests, re-run this session as part of the Phase A/B collateral-regression sweep): "ownership alone grants no clinical access before self-assignment," "`am_i_org_owner()` correctly identifies the real Owner, scoped per organization, and denies a non-owner," "a non-owner Director cannot self-assign capability." Ownership of several organizations is simply several independent rows keyed by `organization_id`; it never touches `profiles.role` and grants nothing platform-wide. **PASS.**

## D3 — Tenant isolation (Organization A cannot read or mutate Organization B's data)

Already covered by `tests/integration/d01OrganizationIsolation.test.ts` (4/4 tests, re-run this session, passing): distinct active caregiver memberships across two organizations stay correctly separated by `get_my_organizations()`/`get_my_staff_patients()`; revoking one organization's membership immediately drops only that organization's data while leaving the other's relationship intact; an entirely unrelated caregiver sees none of the fixture's patients. The new Phase B regression test (`hcnP0RevokedCaregiverClinicalAccessRegression.test.ts`) independently re-confirms the same property for clinical notes specifically ("an UNRELATED organization's active caregiver cannot read this patient's note"). **PASS**, for the memberships/staff/patients/clinical-notes surfaces exercised by these two files. Not exhaustively re-verified for every one of the directive's named surfaces (assignments, documents, conversations, license/billing information) within this pass -- `crossOfficeCommunicationMatrix.test.ts` and `codexF01ConversationConfidentiality.test.ts` (also re-run this session, passing) cover conversations; license/billing cross-tenant isolation was not separately re-executed this pass beyond what the broader regression sweep incidentally exercised.

## Status: **PASS** for D1 (by code/history verification), D2 and D3 (by already-passing, freshly re-run tests) -- no gap found. Direct API access (not just UI-mediated) is exactly what these integration tests exercise throughout.
