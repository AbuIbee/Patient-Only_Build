# 04 — Outstanding Blockers

## Environment blockers

1. **No isolated Vercel+Supabase staging exists.** This is the single largest blocker: every migration in `supabase/migrations/002_*.sql` through `010_*.sql` is written and ready but **unexecuted**, and every RLS/runtime/cross-user-isolation test case in the work order's per-feature "**Test:**" lists is marked BLOCKED in `03_TEST_EVIDENCE.csv` for this reason. Owner decision (2026-10-13) explicitly accepted this: implement code + migrations, run only local static/offline tests, mark runtime claims UNVERIFIED. **Needed to unblock:** a Supabase project separate from `ktehhvmmwnsbcvpjcmzt`, with synthetic patient records, disposable identities, and (for F09/F15) a working email-sending configuration; a Vercel preview or equivalent pointed at it (Vercel preview alone, per the work order, is explicitly NOT staging without a non-production Supabase backing it).

2. **Live Supabase schema is not captured anywhere in version control.** Every migration proposal in this pass had to be written defensively (idempotent, `IF NOT EXISTS`-guarded) rather than as a precise diff against known current state, because the tracked `001_initial_schema.sql` is demonstrably stale (see `00_BASELINE_AND_SCOPE.md`). **Needed to unblock:** a `supabase db diff` or equivalent schema dump from the real project (read-only, consistent with the work order's "production is a read-only evidence source" allowance), so migrations 002–010 can be verified against real column/policy state before any execution is even considered.

3. **No native Android device or emulator was available.** F16's actual OS-level notification delivery (foreground/background/killed-app states, permission denial, timezone/DST behavior) cannot be confirmed without one. The pure scheduling-math helpers (`notificationId`, `toCapacitorWeekday`) are unit-tested and passing; the plugin-integration behavior is not. **Needed to unblock:** an Android device/emulator with the app built via Capacitor (`npx cap sync android` + a debug build), owner-approved per the work order's "Android device tests only in owner-approved isolation" rule (not run in this pass).

4. **`npm run lint` is broken independent of this remediation** — `eslint-plugin-react-hooks@5.2.0` (as pinned in the repo's own, untouched `package-lock.json`) doesn't export `configs.flat.recommended`, which `eslint.config.js` calls directly. This pre-dates this pass (confirmed: the lockfile entry for this package was not touched by `npm install` or `npm install -D vitest`). **Not fixed in this pass** — out of the 16-item scope, and touching `eslint.config.js`/bumping a lint plugin version is exactly the kind of unrelated change the work order's engineering-discipline section asks to avoid. Flagging it here because it means "lint" (the project's one stated automated check, per `CLAUDE.md`) currently cannot run at all, on the baseline or on this branch.

5. **`tsc --noEmit` reports ~570 pre-existing errors**, overwhelmingly `Property 'X' does not exist on type 'never'` because `src/types/supabase.ts`'s generated `Database` type doesn't match what the app already queries. This pass's new code (new RPCs, new columns) adds a handful more instances of the exact same pattern — confirmed via a normalized before/after diff (see `00_BASELINE_AND_SCOPE.md` and `01_IMPLEMENTATION_CHANGELOG.md`), not a new category of defect. **Not fixed in this pass** — the real fix is regenerating `src/types/supabase.ts` from the live schema (`supabase gen types typescript`), which needs DB credentials/access this engagement doesn't have, and is a much larger, separate undertaking than 16 functional repairs.

## Security dependencies (explicit, per work order)

6. **F06 (Memories) is BLOCKED on SEC-003.** The application-side contract (no code change needed — already correct) and the minimal schema proposal (`005_memories_patient_self_access_PENDING_SEC-003.sql`) are both ready, but deliberately withheld from the "ready to apply" set. **Do not apply that migration, or report F06 as complete, until SEC-003 is independently approved and validated** — this is a direct instruction from the work order, not a judgment call made in this pass.

7. **F14 (Calm Me video) is BLOCKED on SEC-006.** Unlike F06, this pass went further than "write a proposal and wait": the insecure write path (uploading patient video into the shared, unreviewed `music-files` bucket) is **actively disabled in the running application code** (`VIDEO_UPLOAD_BLOCKED_PENDING_SEC_006 = true` in `CalmMeDialog.tsx`), per the work order's explicit instruction to "block persistence until SEC-006 secure storage is approved." The dedicated-bucket migration proposal (`008_calm_me_video_PENDING_SEC-006.sql`) is left as commented-out SQL for the same reason. **To unblock:** independent SEC-006 approval, then (a) flip the feature flag, (b) decide on and uncomment/execute the dedicated-bucket migration.

Their logic was verified by direct code review (cited with file:line in `01_IMPLEMENTATION_CHANGELOG.md`) and by the overall `tsc`/`vite build` passes, but **not** by a dedicated unit test. A future pass could extract them into testable pure functions, or add React Testing Library (a new dependency this pass did not request approval for, to keep the dependency footprint minimal).

10. F13's and F14's claims about actual backend storage policy state remain genuinely unverifiable from this repository alone (no storage policy SQL is tracked anywhere) — the migration proposals in this pass are reasoned best-effort proposals, not confirmed fixes to a known-broken state.
