## 3. Corrections to migrations 014, 019, 020, and 023

**020 (profiles RLS self-reference) — real, confirmed, fixed in 024.** Independent evidence-gathering confirmed 020's three admin policies on `profiles` are the *only* case in the entire 001–023 chain of a policy on `profiles` whose own USING clause queries `profiles` again — every other "same EXISTS pattern" 020's own comment cites is a *different* table querying profiles, not profiles querying itself. 024 adds `public.is_admin()` (SECURITY DEFINER, same pattern as 016's `patient_has_paid_entitlement`) and replaces all three policies to call it instead of the inline self-referencing subquery, eliminating the self-reference entirely (a SECURITY DEFINER function owned by the migration-applying role bypasses RLS on its own internal query, same-table or not).

**014 (patients INSERT revoke vs. self-service intake) — real, confirmed, severe, fixed in 024.** `REVOKE INSERT ON public.patients FROM authenticated` (014) and the new `WITH CHECK (id = auth.uid())` policy immediately after it were added back-to-back in the same file. Postgres checks table-level privilege *before* RLS — the REVOKE makes the new policy unreachable for every caller, not just the caregivers it was presumably meant to stop. Confirmed against the real call site: `PatientIntakeForm.tsx:219`'s self-service `.from('patients').upsert({ id: userId, ... })` (userId = the patient's own id) would fail at the privilege layer the first time any patient with no existing row submits intake. 024 restores `GRANT INSERT ON public.patients TO authenticated` — the RLS policy (`id = auth.uid()`) is the actual protection; 014's own `DROP POLICY "Caregivers can create patients"` already independently closes the arbitrary-caregiver-insert path this REVOKE was likely trying to prevent.

**019 (Temporary-demo isolation coverage) — real gap, fixed in 024.** `patient_calendar_notes`, `patient_task_items`, and `patient_routine_items` have no table-level RESTRICTIVE policy and no storage-bucket backstop — none of the three even appears in 019's own "BLOCKERS" comment section as a known gap. `patient_home_photos` has its underlying files incidentally covered by 019's `patient-media` bucket policy, but not its own metadata table. 024 extends the same dynamic, table-existence-tolerant FOREACH pattern 019 established to all four tables (SELECT/INSERT/UPDATE/DELETE), for the Temporary program only — deliberately not added to the separate Companion-expiration list, which is intentionally scoped to just the three approved Free features.

**023 — two gaps found by independent audit, corrected in place** (023 is this same engagement's own unexecuted draft — corrected in place per this project's established convention, not superseded by a new file):
1. The `music-files`/`videos/` RESTRICTIVE policy's `(storage.foldername(name))[1] != 'videos'` branch returns NULL (not false) for any bucket-root object with no subfolder — Postgres RLS treats NULL as denied, so the policy's own "unaffected" claim for non-video content was not actually true for root-level objects. Added an explicit `(storage.foldername(name))[1] IS NULL` branch.
2. The `media_uploads`/`care_partner_checkins` ownership policies only caught `undefined_table`, not `undefined_column` — if the live column isn't actually named `patient_id`, the uncaught error would abort the *entire migration file's transaction*, silently rolling back the subscriptions and music-files fixes too. Added `WHEN undefined_column` guards to both.

## 5. Medication-history preservation and import behavior

**All three legacy-localStorage migrations (medications, calendar notes, tasks) rewritten to reconcile by a persisted per-record progress set, not gated on "destination table empty."** Previously, after even one successful insert, the "table is empty" gate became permanently false, silently stranding every remaining unmigrated record forever with no retry path. Now each migration tracks which local record ids are confirmed persisted (`src/lib/legacyMigration.ts`: `loadMigratedIdSet`/`saveMigratedIdSet`/`filterPending`/`isFullyMigrated`, shared by all three call sites) and only clears the local source once every record is accounted for.

**Dose history (`patientLocalLogs`) is now actually migrated — it was not before.** The previous version of `PatientMedications.tsx`'s migration block referenced `patientLocalLogs` exactly once, to delete it unconditionally, without ever reading or inserting it anywhere — every patient's historical dose-taking record predating backend storage was being silently and permanently destroyed on first migration, success or failure. Dose logs are now migrated after their own medication has a confirmed new id (via a local-id → new-id map), with the same per-record reconciliation guarantee, so a log cannot be duplicated on retry and cannot be dropped if its medication's insert failed this round.

**Known, unresolved tension (flagged for owner decision, not silently resolved):** `PatientLayout.tsx:426`'s `handleLogout` deliberately wipes `patientLocalMeds`/`patientLocalLogs`/`patientCalendarNotes`/`patientMyTasks` from localStorage on every sign-out, labeled "Clear all patient PHI from localStorage before signing out (HIPAA)." If a migration is only partially complete (e.g. a network failure left some records pending) and the patient then logs out — including via the existing 10-minute inactivity auto-sign-out — this HIPAA-driven wipe would destroy the still-unmigrated local source data, defeating the reconciliation fix above for that specific timing window. This is a genuine conflict between two legitimate requirements (HIPAA PHI-at-rest minimization vs. never losing unconfirmed health records) that this pass did **not** resolve in either direction — logout behavior was left exactly as-is, since overriding a deliberately-labeled compliance measure is an owner policy decision, not an engineering judgment call to make silently.

## 6. Document, media, and emergency-function repairs

- **`PatientDocuments.tsx` had a real, confirmed-reproducible crash bug**, independent of anything else in this engagement: `loadDocs('medical_bills')` (called unconditionally on every mount) referenced `setBillsLoading`, and `handleBillUpload` referenced `setBillUploading` — neither was ever declared anywhere in the file. Both are `ReferenceError`s at runtime (TS caught them as `TS2552: Cannot find name`, once `-p tsconfig.app.json` was actually used — see §7). The Bills tab's loading/uploading state was simply absent. Fixed: both state variables added, wired into the same loading-spinner/"Uploading…" pattern the Documents tab already had.
- **Storage-removal results across 9 call sites were previously unchecked** (`ShowMeHomeDialog.tsx` ×3, `PatientHome.tsx` ×3, `PatientDocuments.tsx` ×1, `mediaService.ts` ×2, `PatientMemories.tsx` ×1 — the last one pre-existing, not from this engagement's own earlier work): a bare `await supabase.storage...remove(...)` with no captured result, so a failed cleanup was completely silent — not logged, not surfaced, not distinguishable from success. All nine now capture `{ error }` and log it. None of these needed a user-facing error: in every case the *authoritative* record (the DB row) was already correctly created or removed by that point — an orphaned storage object is an operational-hygiene issue, not a data-correctness one, and surfacing it to the patient as an error would misrepresent an operation that, from their perspective, succeeded.
- **`PatientMemories.tsx`'s `handleRemove`** had the same storage-before-DB ordering defect already fixed elsewhere in this engagement (FQA-027) — not previously touched. Reordered to delete the DB row first, with UI rollback and a toast on failure, matching the established pattern.
- **Emergency dialog (`PatientHome.tsx`) corrected beyond the earlier FQA-020 fix.** The dialog previously said "Help is Coming" / "Calling {phone}..." as stated fact. Per the stricter instruction here: the app cannot confirm a dialer opened, a call connected, or that anyone was reached — `tel:` links can silently do nothing on a device with no SIM, no dialer, or a canceled call. Copy changed to describe only the confirmed app action ("We tried to start a call to {phone}") and give the patient an explicit fallback ("If your phone's call screen did not open, tap Call Now... Or ask someone nearby for help right away"), never asserting an unverified outcome.
- **Voice-recorder race (FQA-023) — re-verified unchanged from the prior pass**, already fixed: `doSave` awaits `onSave` and only closes on confirmed success.
