# 05 — Remaining Blockers (MYMEMORIA-CLAUDE-CORRECTIVE-001)

## F10 / FQA-016 / SEC-004
- **Migration 011 is unexecuted.** Applying it requires the same isolated staging environment every prior report in this engagement has flagged as absent. Until applied, the live `subscriptions` table's client-writable policies remain in force in reality, regardless of what this branch's code or migrations propose.
- **Policy predicates were inferred from names and prose, not from the literal SQL.** The evidence document (`04_SUPABASE_SECURITY_AND_SCHEMA.md`) gives policy names, commands, and a prose description of behavior, not the exact `USING`/`WITH CHECK` clauses. The `DROP POLICY IF EXISTS "<name>" ON subscriptions` statements in `011` are safe regardless (a `DROP POLICY IF EXISTS` either removes exactly the named policy or no-ops if the name doesn't match — it cannot accidentally drop or weaken anything else), but if any of those eight names is wrong or renamed on the live system, the corresponding risk would remain unaddressed. **Recommend: before applying, run `SELECT policyname, cmd, qual, with_check FROM pg_policies WHERE tablename = 'subscriptions'` against the live project (read-only) and confirm the eight names match exactly.**
- **`status` CHECK constraint exact values unconfirmed.** FQA-011 suggests the live constraint may exclude `'trialing'`; this was not independently verified. `admin_set_subscription()` still validates against a list that includes it; a live mismatch would surface as a visible `CHECK` violation (safe failure), not corrected proactively here given no confirmed evidence either way.
- **`Service role full access` / `Service role subscriptions`** were left untouched on the assumption they are correctly scoped to the real `service_role` Postgres role. This assumption is reasonable (consistent with how Supabase service-role policies are conventionally named and with `service_role`'s `BYPASSRLS` default) but not independently confirmed against the live `pg_policies.roles` column. **Recommend confirming this before relying on it.**
- **profiles.role self-escalation (SEC-002) is a related, unaddressed risk.** The same evidence document separately flags that `profiles_update`'s policy permits an ordinary user to change their own `role` column at the database layer (`id=auth.uid() OR is_admin_check()` with no role-change guard) — meaning even after `subscriptions` is locked down, a sufficiently motivated user might attempt to self-promote to `admin` and then legitimately call `admin_set_subscription()` themselves. **This is SEC-002, explicitly out of this correction's named scope (F10/FQA-016 and F16/FQA-010 only) — flagged, not fixed, here.**

## F16 / FQA-010
- **No device or emulator test was performed.** The 8-step device acceptance plan in `03_ANDROID_NOTIFICATION_INTEGRATION.md` is entirely unexecuted. Static/build verification (tsc, vite build, unit tests) all pass, but none of that is runtime proof of actual notification delivery, reboot survival, or timezone behavior on a real device.
- **The manifest-merger conclusion was verified by static inspection of the installed package and Gradle wiring, not by inspecting an actual built APK's merged manifest.** The standard tooling for that (`./gradlew :app:processDebugManifest` output, or unzipping a built APK/AAB and reading `AndroidManifest.xml` with `aapt dump xmltree`) was not run — this engagement has no Android build toolchain available, only the JS/TS side. The conclusion rests on well-established, standard Android Gradle Plugin manifest-merger behavior and on confirming none of the override conditions that would prevent it (no `tools:node="remove"`, module genuinely included in the build), which is a sound basis for the conclusion but is one level removed from inspecting the artifact directly.
- **FQA-006's separate claim (the live `reminders` table itself may not exist)** was neither confirmed nor refuted by this corrective pass. If true, F16's notification-scheduling fix is necessary but not sufficient — the feature's data layer (unrelated to this pass's notification-permission work) would still need the `reminders` table to actually exist and be populated. Not investigated further: no live schema access, and this corrective pass's scope was specifically the manifest/permission/duplicate-prevention/denied-state items named in the correction order, not the broader data-layer question.
- **The native notification-channel ID is left at the plugin's default.** Not a functional blocker (the plugin creates a default channel automatically), but a cosmetic item (the channel would show as a generic name like "Default Channel" in Android's notification settings rather than something branded like "Reminders") that a future pass could address with a `channelId` parameter on each scheduled notification — intentionally not added here, since it isn't necessary for correctness and the correction order asked for "only necessary" changes.
