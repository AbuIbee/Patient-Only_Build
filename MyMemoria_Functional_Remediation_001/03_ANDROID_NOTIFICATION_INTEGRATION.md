# 03 — Android Notification Integration (F16 / FQA-010)

## What changed since the original F16 pass
The original implementation pass wrote the JS/Capacitor scheduling layer (`src/lib/reminderScheduler.ts`) while `node_modules` in this clone was a non-functional stub — the actual `@capacitor/local-notifications` package and the native Android project could not be inspected at that time. The subsequent Codex-style independent-verification pass read only the **app-level** `android/app/src/main/AndroidManifest.xml` (which declares just `INTERNET`/`BILLING`) and concluded the fix "would likely not function on a real Android 13+ device." That conclusion was **incomplete** — it did not check whether Android's manifest merger would supply the missing permissions from the plugin's own library manifest. This pass re-examined that specifically.

## What was inspected (all read-only, no execution)
1. **The installed plugin's own manifest:** `node_modules/@capacitor/local-notifications/android/src/main/AndroidManifest.xml` (version `8.0.2`, confirmed via its `package.json`). It declares:
   - `<uses-permission android:name="android.permission.POST_NOTIFICATIONS"/>`
   - `<uses-permission android:name="android.permission.RECEIVE_BOOT_COMPLETED"/>`
   - `<uses-permission android:name="android.permission.WAKE_LOCK"/>`
   - Three `<receiver>` entries: `TimedNotificationPublisher`, `NotificationDismissReceiver`, and `LocalNotificationRestoreReceiver` — the last with an explicit `BOOT_COMPLETED`/`LOCKED_BOOT_COMPLETED`/`QUICKBOOT_POWERON` intent-filter and `android:directBootAware="true"`, i.e. the plugin ships its own reboot-survival mechanism natively.
2. **Whether the plugin is actually wired into this project's native build** (a real, separate risk — a package.json dependency alone proves nothing if `npx cap sync android` was never run to register it): confirmed yes, via `android/capacitor.settings.gradle` (`include ':capacitor-local-notifications'` pointing at the real `node_modules` path) and `android/app/capacitor.build.gradle` (`implementation project(':capacitor-local-notifications')` in its `dependencies` block). Both files carry the generator's own "DO NOT EDIT — regenerated by capacitor update" header, confirming they were produced by a real `npx cap sync`/`capacitor update` run at some point, not hand-written.
3. **Target/compile SDK:** `android/variables.gradle` sets `compileSdkVersion = 36`, `targetSdkVersion = 36`, `minSdkVersion = 24`. `targetSdkVersion` ≥ 33 is exactly the threshold at which `POST_NOTIFICATIONS` becomes a required runtime permission for any notification to display — confirming the permission genuinely matters for this specific build configuration, not hypothetically.

## Conclusion: no `AndroidManifest.xml` edit was necessary
Android's standard manifest-merger tool (part of the Android Gradle Plugin, not something this project configures specially) unions `<uses-permission>` and `<receiver>` declarations from every included library module into one final merged manifest at build time, unless a module's manifest is explicitly excluded with `tools:node="remove"` — no such exclusion exists anywhere in this project's `AndroidManifest.xml` (confirmed by direct read, full file, during the earlier verification pass). Since the plugin module is genuinely included in the Gradle build (point 2 above) and its own manifest already declares everything required (point 1), the **final built APK's manifest already contains `POST_NOTIFICATIONS`, `RECEIVE_BOOT_COMPLETED`, and `WAKE_LOCK`**, without any change to the app-level manifest file. Editing it further would have been a redundant, unnecessary change under the correction order's "implement only necessary manifest/config/permission handling" instruction.

**This corrects the earlier verification pass's finding.** That finding was not fabricated — the app-level manifest genuinely does not list these permissions — but it was incomplete, since it stopped short of checking merge-time inclusion. That correction is recorded here rather than silently absorbed.

## Exact-alarm permission: considered, not added
`SCHEDULE_EXACT_ALARM` (or the stricter `USE_EXACT_ALARM`) was evaluated and deliberately not added:
- Medication/task/appointment reminders in this app tolerate a delivery window of a few minutes without meaningfully harming the user experience — this is not an alarm-clock or time-critical-dispatch use case.
- Requesting `SCHEDULE_EXACT_ALARM` on a targetSdk-33+ app surfaces additional Google Play Console policy requirements (a declared use-case justification, subject to review) — out of scope per "no signing or Play changes."
- Without it, Android schedules the plugin's alarms inexactly (subject to batching/Doze-mode deferral of up to several minutes), which is the correct, conservative default for this feature's actual precision needs.
- This decision is recorded, not merely defaulted to, satisfying "exact-alarm permission only if justified" by explaining why it is not.

## What WAS changed, and why it was the real gap
Re-reading `src/lib/reminderScheduler.ts`, the actual gap was not the manifest — it was that `syncReminderNotifications()` returned `void`. A denied notification permission (a realistic outcome: Android 13+ requires an explicit runtime grant, which users may decline) resulted in the function silently returning with no observable effect anywhere in the UI. `PatientReminders.tsx` still displayed "You'll see notifications at the scheduled times" regardless of whether that was true. This is exactly the category of false claim the work order's engineering-discipline section prohibits ("do not claim reliable background delivery").

Fixed by:
1. `syncReminderNotifications()` now returns `Promise<ReminderPermissionStatus>` (`'granted' | 'denied' | 'unsupported'`) instead of `Promise<void>`, with no change to its actual scheduling/cancellation behavior.
2. `PatientLayout.tsx` awaits that result and stores it in state, passed down as `reminderPermissionDenied` to `<PatientReminders />`.
3. `PatientReminders.tsx` renders a visible, truthful "Notifications are turned off" card when denied, directing the user to device settings — instead of silently doing nothing while the unconditional "You'll see notifications..." copy remains unchallenged.

## Reboot and timezone handling
Both are handled natively by the plugin, not by application code, and were verified to exist rather than assumed:
- **Reboot:** `LocalNotificationRestoreReceiver` (confirmed present in the plugin's Java source and registered in its manifest with the boot-completed intent-filter) re-persists/reschedules pending notifications after a device restart. No app-level code is involved or needed.
- **Timezone/DST:** the `schedule.on.{weekday,hour,minute}` recurring-trigger shape this app uses is evaluated against the device's current wall-clock/timezone setting by the OS's `AlarmManager` on each occurrence — a timezone change or DST shift is reflected automatically on the next firing without custom handling. `reminderScheduler.ts`'s own time parsing (`reminder.time` as an `"HH:MM"` local-time string) is consistent with how the rest of the app already treats schedule times (e.g. `PatientMedications.tsx`), so no inconsistency was introduced.

## Duplicate prevention
Unchanged from the original pass, re-verified: `syncReminderNotifications()` calls `LocalNotifications.getPending()` and cancels every pending notification before scheduling the current reminder list from scratch, on every call. This is a correct-by-construction duplicate-prevention strategy (no partial-diff logic to get wrong), confirmed by the new test `cancels previously-pending notifications before rescheduling (duplicate prevention)` in `tests/unit/reminderScheduler.permission.test.ts`, which asserts `cancel()` is invoked strictly before `schedule()`.

## Device acceptance plan (not executed — no device/emulator available in this engagement)
1. Install a debug build (`npx cap sync android` then build/run from Android Studio or `./gradlew assembleDebug`) on a device/emulator running API 33+ (to exercise the `POST_NOTIFICATIONS` runtime-permission path this build actually targets).
2. **Fresh install, first reminder screen visit:** confirm the OS permission prompt appears exactly once; grant it; confirm no "notifications are off" banner renders.
3. **Deny path:** on a second fresh install (or after revoking the permission in system settings), visit the reminders screen; confirm the "Notifications are turned off" banner renders and no crash/hang occurs.
4. **Delivery:** create a reminder a few minutes in the future; background the app; confirm the notification arrives within a few minutes of the scheduled time (not exact-alarm precision, by design).
5. **Reboot survival:** schedule a reminder for the next day, reboot the device, do not reopen the app; confirm the notification still fires at the scheduled time the next day.
6. **Timezone change:** with a reminder scheduled, change the device's timezone; confirm the next occurrence fires at the new local wall-clock time, not the original timezone's equivalent instant.
7. **Edit/delete, no duplicates:** edit an existing reminder's time or delete it, then wait past the original scheduled time; confirm exactly one (or zero, if deleted) notification fires — never both the old and new time.
8. **Logout:** sign out while reminders are scheduled; confirm (via system notification-schedule inspection, e.g. `adb shell dumpsys alarm`, or simply waiting past a scheduled time) that nothing fires after logout, per `App.tsx`'s `cancelAllReminderNotifications()` call on `SIGNED_OUT`.

None of steps 1–8 were performed by this engagement. They require a physical device or emulator and a native build, both outside this session's available tooling.
